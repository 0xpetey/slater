# AppKit's app lifecycle, not SwiftUI's `App`

Slater's windows are all AppKit (the status item, Shots, onboarding, notices) hosting SwiftUI views; the SwiftUI `App` entry point was providing one thing, the `Settings` scene. Measured on 2026-10-02 (M1, macOS 26.6, warm launch, logged by `LaunchTiming`), SwiftUI's lifecycle cost about 50 ms of the time from process start to a usable menu bar item: about 35 ms before our delegate was reached and about 16 ms of its own `applicationWillFinishLaunching` and scene creation; the Screen Recording preflight, run synchronously at startup, cost another 11 ms. The private `showSettingsWindow:` selector the status menu used to open the scene had also stopped opening anything on macOS 26. So the app runs on `NSApplicationMain` with a `main.swift`, Settings is a window of our own (`SettingsWindowController`), the permission check runs off the main thread after the item is up, and the main menu, which a menu bar app never shows but whose key equivalents work in its windows (⌘, and ⌘Q, ⌘W, the Edit items), is a minimal one built by hand (`MainMenu`) the first time one of Slater's windows becomes key, since it costs about 5 ms. Result: about 120 ms to the menu bar item instead of about 165 ms. What remains is the system's: dyld about 20 ms, `NSApplication.shared` about 60 ms, AppKit's own launch about 20 ms, and the status item's creation about 20 ms; Slater's own work before the item is about 1 ms.
